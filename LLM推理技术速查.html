① 主流推理引擎对比 覆盖在线服务主战场：vLLM / SGLang / TensorRT-LLM 等

判断一个引擎，先看三件事：批处理机制（吞吐根基，见 ④）、硬件生态（可部署到哪）、工程化配套（路由 / 集群 / PD 分离）。 训练框架与端侧 NPU 工具链不在本页范围。

vLLMUC Berkeley Sky Computing Lab 起源 · Apache-2.0
社区事实标准 · 多硬件生态最广
招牌机制
PagedAttention + 连续批处理；V1 引擎统一 prefill/decode 调度（v0.8.0 起默认），chunked prefill、prefix caching 默认开启；调度按固定 token 预算切步，天然支持长输入分块。
生态硬件
NVIDIA / AMD / Intel / TPU 官方支持，昇腾（vllm-ascend）、海光、寒武纪、摩尔线程等有后端插件；OpenAI 兼容 API、生产栈（Kubernetes Router）配套完整。
适用场景
通用在线服务默认首选；多硬件平台交付；从研究验证到大规模生产的完整路径；PD 分离集群化（1P1D / XPYD）由官方主线推进。
注意边界
流水线并行（PP）在 V1 重构中回归（此前为 V0 能力），跨机 PP 以官方文档为准；单点极致性能常被专用栈（TRT-LLM）反超。
SGLangLMSYS 社区 · Apache-2.0
极致吞吐 · RadixAttention 前缀复用
招牌机制
RadixAttention：按前缀树管理 KV 缓存，多轮对话 / 相同系统提示词场景命中率高；调度与 kernel 深度调优，公开基准吞吐常领先。
生态硬件
NVIDIA / AMD 主力，昇腾等国产平台积极适配；DeepSeek 系优化深入（DP attention、DeepEP、EPLB、两批重叠）。
适用场景
高并发在线服务、MoE 大模型服务、Agent / 多轮长前缀复用场景；公开复现：12 节点 × 8 H100（96 卡）服务 DeepSeek-V3/R1，PD 分离 + DeepEP + EPLB，2k 输入口径下每节点 52.3k 输入 / 22.3k 输出 token/s（2025-05，LMSYS）。
注意边界
模型与生态覆盖弱于 vLLM；版本迭代快，生产锁定版本需回归测试；部分高级特性文档滞后于代码。
TensorRT-LLMNVIDIA · Apache-2.0 开源（深度绑定 TensorRT 生态）
NVIDIA 集群单机密度与延迟标杆
招牌机制
in-flight batching（连续批处理 NVIDIA 术语体系）+ paged KV cache；深度绑定 CUTLASS / cuBLAS / FlashInfer kernel 库，AOT 编译 + CUDA Graph 去除运行时调度开销——「单实例」指单个引擎进程（单卡或一个 TP/PP 卡组，多实例即 ② 节 DP 副本扩展），其绝对性能上限高；总吞吐 ≈ 单实例吞吐 × 副本数，副本基数即 DP 扩容天花板。
生态硬件
仅 NVIDIA；官方 BLS 容器、NVIDIA Dynamo（路由层）联动，NVL72 等机柜级方案首选栈之一。
适用场景
延迟敏感（TTV 首字）型 API、大流量 NVIDIA 生产集群、英伟达硬件的极致性价比压榨。
注意边界
生态深度绑定 NVIDIA（TensorRT 编译器闭源）；新模型 / 新量化格式（GGUF 类社区格式）跟进节奏慢于开源栈；编译与调优门槛高，运维复杂度大；Windows 主线支持已于 0.18.0 弃用（转向独立的 TensorRT for RTX）。
llama.cpp / Ollama开源社区 · MIT
端侧与本地推理
招牌机制
GGUF 量化格式（Q4_K_M 等），纯 CPU / 消费级 GPU 可跑数十 B 模型；llama.cpp 是内核，Ollama 在其上封装「拉模型即用」体验。
生态硬件
Mac（Metal）、Windows/Linux（CUDA/Vulkan/ROCm）、CPU only 全覆盖。
适用场景
个人本地助手、隐私敏感数据、离线环境、原型调试；量化生态成熟（社区模型 GGUF 版本最全）。
注意边界
面向单用户小并发设计，不是服务端引擎；长上下文吞吐与并发能力与 vLLM 类引擎差一个量级以上。
DeepInferDeepSeek-AI · Apache-2.0 · 2026-10 开源
DeepSeek 官方生产推理引擎开源版
招牌机制
DeepSeek 自研 kernel 全家桶（FlashMLA / DeepGEMM / DeepEP / TileKernels + 定制 TileLang kernel）；DSpark 置信度调度投机解码（并行 backbone + 轻量序列头起草，置信度决定验证预算，最大 draft 长度默认 5，见 ⑤ 节）；Attention DP / balanced CP + MoE EP + EPLB；异步调度（CPU 批调度与 GPU 执行重叠，默认开启）；另有批不变推理、确定性采样（均限 NVIDIA）与结构化输出（regex / JSON schema / EBNF）。官方致谢：基于 vLLM 深度定制，借鉴 SGLang 与 TRT-LLM。

适用场景
DeepSeek 模型生产级吞吐部署（官方 App 同款引擎）；大规模离线推理（合成数据 / 蒸馏 / 评测）；研究生产级 MoE 推理工程（EPLB、置信度投机解码、异步调度的参考实现）。

② 四种主流并行：TP · PP · DP · EP 原理 · 优势 · 硬件配置要求

速查主线：TP 切矩阵、PP 切层、DP 切请求、EP 切专家。前三种对 dense 与 MoE 模型通用； EP（Expert Parallelism，专家并行）是 MoE 模型的专属切片方式，也是 DeepSeek-V3 生产部署的核心。

TP张量并行 Tensor Parallelism · 切权重矩阵
原理
把每层权重矩阵按列 / 行切块分散到多卡：每卡只算部分矩阵乘，再 all-reduce 汇总结果。对被并行用户透明，单卡逻辑几乎不变。
优势
单卡显存需求近似 ÷TP；无流水线气泡，小 batch / 单请求也能受益，是降低单请求时延最直接的并行。
硬件要求
高带宽片内互联必备（NVLink / NVSwitch；国产卡看对应片内互联能力）。通信每层两次、延迟敏感，故一般 不出机柜节点：
常用取值
TP = 节点内 GPU 数，典型 TP2 / TP4 / TP8；DeepSeek-V3 官方口径仅 TP4（控制通信开销）。
PP流水线并行 Pipeline Parallelism · 切层阶段
原理
按 transformer 层切成若干阶段（如 80 层切 4 段），微批次像流水线一样逐段流动；阶段间只传边界激活值（通信量小）。
优势
通信量最小、可跨节点走 IB / 以太；把「单机装不下」变成「多机拼装」，扩展显存上限；对互联要求低于 TP。
硬件要求
普通 RDMA / 以太即可；但需要足够大的并发（微批数）填满流水线，低流量时段空转严重。
代价
气泡降低有效利用率；单 token 穿越所有阶段，首字时延略增；训练用 1F1B / 交织式调度压缩气泡，推理靠在途请求数填充。
DP数据并行 Data Parallelism · 切请求
原理
每个卡组持一份完整模型副本，上层把不同请求分给不同副本；模型本身不切片。推理无反向传播，副本间零通信（训练时才有梯度同步）。
优势
吞吐最干净的扩展方式（近线性）；实现简单；对互联零要求；是最便宜的横向扩容手段。
硬件要求
每个副本须独立容纳完整模型（或副本内部再嵌 TP）；前端需要请求级负载均衡：vLLM 生产栈 Router、SGLang Router 等承担此事。
常用取值
与 TP 组合时 DP = 总卡数 ÷ TP 组规模；DeepSeek-V3 官方口径 prefill DP8 / decode DP80。
EP专家并行 Expert Parallelism · MoE 切专家
原理
MoE 模型专属：把不同专家放到不同 GPU，token 经 router 找到专家所在卡（dispatch），算完再送回（combine），每层 all-to-all × 2。
优势
容纳单机放不下的超大 MoE；专家批集中后万卡级服务可行；配合冗余专家 / EPLB 可以压平热点。
硬件要求
RDMA / IB + 工程化是硬门槛；跨机 all-to-all 时延直接决定收益，推荐 DeepEP 类专用 kernel 与 IBGDA/GPUDirect 直传。
官方口径
DeepSeek-V3：每 token 激活 8 专家 + 1 共享；prefill EP32（4 节点 32 卡，每卡 8+1 专家，32 个冗余专家）；decode EP320（40 节点 320 卡，每卡仅 1 专家，64 卡托管冗余 + 共享专家）。
从属并行，知道即可：SP（序列并行）常与 TP 联用，减少 LayerNorm / Dropout 处的通信；CP（上下文并行）把超长序列按维度切块， 主要服务长上下文的 prefill/微调阶段。速查主线抓住 TP 切矩阵、PP 切层、DP 切请求、EP 切专家 四主轴，其余按框架文档选配。

并行组合速查（怎么拼）

场景起点推荐组合一句话理由
模型单卡放得下（≤ 约 14B）纯 DP（多副本 + 前端 Router）吞吐近线性扩展，层内零通信，实现与运维最简单
单机 8 卡可容纳（70B 级 dense）TP8（或 TP4×DP2）TP 不出节点，NVLink 内消化通信；小 batch 延迟最稳
dense 模型跨机（405B 级）TP8 × PPnTP 留在机内，PP 只传边界激活跨机走 IB，通信量最小
大型 MoE（DeepSeek / Qwen-MoE 级）TP + DP + EP（+ 冗余专家 / EPLB）按官方部署口径拼装；decode 做小 TP、大 EP 以压时延
长上下文 prefill 成为瓶颈上述组合 + CP / 长 chunk 切分序列维再切一刀，缓解单步计算过长、配合 PD 分离更顺

③ PD 分离架构 Prefill–Decode Disaggregation · 预填充/解码解耦

一条请求分两段：prefill（预填充）一次性吃整个输入，算力受限 compute-bound； decode（解码）逐 token 生成，每步都读全量权重 + KV，访存受限 memory-bound。 两者资源画像几乎相反，混在一池 GPU 里就会互相干扰——这是 PD 分离的全部动机。

客户端prompt + 流式输出 → 路由器 / 网关按 SLO 与 KV 位置分发请求 → Prefill 池计算受限 · 大 batch · 长输入切片处理
产出 KV Cache KV 迁移 → Decode 池访存受限 · 常驻大 batch
逐步生成 token
解码 token 流式返回客户端（ITL 平稳不再被长 prefill 打断）

KV 迁移通道：分离成败的关键

传输量 = KV 张量大小（与上下文长度、KV 精度成正比）。长上下文场景下 KV 迁移本身可占可观带宽，通道选型三级：

A机内 / 超节点直连
NVLink / NVSwitch 域内（如 NVL72 整机柜）跨卡直传，时延最低、工程最简单；超节点架构把 PD 分离半径缩到机柜内。
B跨机 RDMA（上规模主流）
IB / RoCE + GPUDirect / IBGDA 绕过 CPU；传输层代表：NIXL（vLLM V1 后端）、Mooncake（Moonshot 开源）、HiRad、NVSHMEM / UCX 系。
C内存 / SSD 分级中转
KV 先落 CPU 内存或本地 SSD（LMCache 类分级缓存），容量换带宽；prefill 池可即时释放显存，适合输入超长 + 命中复用场景。

主流引擎 PD 能力现状（以官方文档为准）

vLLM V1：1P1D / XPYD 拓扑，NIXL 传输后端 + 生产栈 Router（KV 感知调度），官方主线方向 SGLang：PD 分离原生支持，Mooncake / HiRad 等传输集成，DeepSeek 服务公开案例 TensorRT-LLM：disaggregated serving + NVIDIA Dynamo 路由，NVL72 官方参考架构 MindIE 等：同类能力随昇腾 CANN 版本演进，选型前查 release notes
收益（为什么值得）
  • ITL 平稳：解码不再被长 prefill 打断，尾延迟（P99）显著收敛；
  • 两池独立伸缩：输入长就扩 P 池、输出长就扩 D 池，不再整池复制；
  • 硬件可异构：P 池选高算力、D 池选大显存高带宽，卡型可分开选型；
  • goodput 提升：公开研究口径（DistServe / Splitwise / Anyscale 等）同 GPU 同 SLO 下 1.3~2.3×——但注意口径是 SLO 内有效吞吐，不是裸吞吐。
代价（什么场景别上）
  • KV 迁移开销：长上下文下传输量与延迟不可忽视，通道设计是第一风险点；
  • 架构复杂度：多一跳路由与两池容量规划，运维 / 排障成本上升；
  • 负载太轻不划算：并发不足时 P、D 两池互相空转，反而劣化；
  • 共址已够用的场景：中小规模用 共址 + chunked prefill + prefix caching 通常下就够了，不必为分离而分离。
速判：输入长、流量大、SLO 敏感、突发多的生产服务 → PD 分离是标配路线； 量小、输入短、内部工具型服务 → 共址 + chunked prefill 先跑，观测到 ITL 尖刺再考虑分离。

④ PagedAttention · RadixAttention · Continuous Batching KV 显存与批调度三机制

KV Cache 是在线推理第一瓶颈（见下方计算器）。本节三个机制是一条递进链： PagedAttention 管好 KV 的「存」（分页消除浪费）→ RadixAttention 管好 KV 的「用」（前缀复用）→ Continuous Batching 管好 GPU 的「批」（任意步换发请求）。三件都是行业标配； 批调度一族术语繁多（iteration-level scheduling / continuous batching / in-flight batching），本节一并讲清。

先辨析一对最易混淆的概念：FlashAttention ≠ PagedAttention。 FlashAttention 是 kernel 级优化——把 attention 计算分块（tile）流式执行，不落完整 N×N 注意力矩阵，解决的是「算得快」（IO 感知，减少 HBM 读写）； PagedAttention 是显存管理——KV 按块分页、按需分配，解决的是「放得下」（消除碎片、提高并发）。 两者正交且可叠加：现代引擎的 attention kernel 既用 FlashAttention 式分块计算，又从分页块中读取 KV（FlashInfer 等 kernel 库即做此事）。
问题起点：每生成一个 token，都要重读全部权重与该请求的 KV，KV Cache 随上下文线性膨胀。 传统做法按最大长度为每个请求整段连续预留显存，实际用不满 → 论文口径：浪费 60%~80%（内部碎片 + 外部碎片 + 超额预留） 显存利用率低直接限制并发 batch 大小，吞吐上不去。
  1. 分页：KV 按固定大小切块（典型 16 token / 块），逻辑上用「块表」把不连续的物理块串成一条序列，按需分配、用完即回收进空闲池;
  2. 浪费收敛：只有每请求最后一块可能半空，浪费 <4%（论文口径），接近消除碎片；
  3. 解锁连续批处理：块粒度回收让请求可以在任意步完成退出、新请求随时加入（continuous batching），GPU 不再等整批；
  4. 解锁前缀复用：相同的系统提示词 / 多轮历史命中同一批 KV 块，prefix caching 直接跳过重复计算（块哈希 + 引用计数）——SGLang 把它做成前缀树，见下 RadixAttention。

RadixAttention（SGLang）：把前缀复用做成一棵「基树」

问题：PagedAttention 的 prefix caching 按「整条前缀」命中——多轮Agent 对话里， 每轮历史只是上一轮再追加几行，前缀其实层层嵌套；不同请求命中前缀长长短短，要能各自停在树的不同高度。
  1. 组织：所有历史请求的 KV 块按前缀挂进一棵 radix tree（基树）——公共前缀只存一份，节点分叉处才分开存；树节点带引用计数 + LRU 淘汰（内置监控里就是「hit rate」指标）；
  2. 命中：新请求先在树上匹配，匹配到哪一层就直接复用到哪一层（部分命中也是收益），只对未命中的尾部做 prefill；
  3. 效果：系统提示词 / few-shot 模板 / 多轮对话这类「共享前缀」负载，TTFT 大幅下降（命中部分不用算）， 显存里一份 KV 服务万条分枝——这是 SGLang 在 Agent / 多轮负载上吞吐领先的看家机制；
  4. 代价与边界：前缀粒度带管理开销，前缀几乎不重复的负载（如每条 prompt 都是独立长文）收益趋零，此时退化为普通 PagedAttention 场景——按业务分布选机制，不看名气。
图示：radix tree 上的前缀共享（共享段只存一份 KV）
新请求「对话 A 第3轮」沿树匹配到「对话 A 第2轮」整条路径，只有新增的一轮需要 prefill；「问题 B」命中到「知识库片段 A」层，分叉以下才计算。命中越深，省得越多。

Continuous Batching（连续批处理）：GPU 不再「等整批」

问题：最朴素的静态批处理（static batching）把一批请求捆到整批最慢请求为止—— 生成长度参差时先完成的请求在批里干等，算力大量空转。 三个名字，一个机制：Orca（OSDI'22）提出 iteration-level scheduling（迭代级调度）； vLLM 论文（SOSP'23）沿用 continuous batching 术语并随 PagedAttention 普及；NVIDIA TensorRT-LLM 产品名叫 in-flight batching（官方文档注明与前两者同义，其实现捆绑 paged KV cache）。
  1. 调度器主循环（每步 forward 前做四件事）：① 摘除本步完成的请求并回收其 KV 块；② 先服务 running 队列的 decode，再在本步 token 预算内从等待队列吸收新请求；③ 打包「decode 全体 + prefill 切片」一次前向；④ 采样输出、回到 ①。GPU 任何一步都不空转；
  2. prefill 与 decode 混跑：同一批里既有算 prefill 的也有算 decode 的，slot 随完成随释放、随排队随补位（以 vLLM V1 的统一调度为代表，chunked prefill 与 prefix caching 由此默认开启、零配置）；
  3. 效果：Orca 论文（OSDI'22）在 GPT-3 175B 上对比 FasterTransformer，同延迟级下吞吐 36.9×——这是迭代级调度对静态批的公开基线口径，增益大小取决于生成长度差异（长度越参差收益越大）；vLLM 论文（SOSP'23）另报同延迟下 2~4× 吞吐（对比 FasterTransformer / Orca）。
  4. 代价：批内动态插队使序列长度参差——decode 优先时新请求 TTFT 排队；反之 prefill 抢跑会打断 decode 造成 ITL 尖刺。这一矛盾正衔接 ③ PD 分离的动机。
配套机制 · chunked prefill：长输入按固定 token 预算切片、多步吃完（不占满单步、不饿死同批 decode）—— 即 ③ 节「共址 + chunked prefill」方案里的同名机制，本机制的重要组成部分而非可选项。 与其他机制的关系：continuous batching 负责「批怎么换」，PagedAttention 负责「KV 存得下」，RadixAttention 负责「别重复算」——三者叠加才凑齐高吞吐推理，缺一不可。
图示：静态批 vs 连续批处理的时间线
A 提前完成后其 KV 块即刻回池，slot 立刻给排队的 D/F；B 自顾自继续生成。引擎每步 forward 前完成这轮「换发」，GPU 从不空等整批。

KV 压缩：量化之外的三条路（改写「全量 KV 常驻显存」前提）

④ 节计算器的前提是全量 KV 常驻显存；KV 压缩技术改写这个前提本身。与 ⑥ 节 KV 量化（降精度）互补，这里是降条目数的三条路线：

A剪枝驱逐
H2O（Heavy-Hitter Oracle）：保留「重击者」token 的 KV，驱逐低分 token；StreamingLLM：保留开头 attention sink + 滑动窗口，实现流式无限长度。代价：有损，长上下文召回任务需按业务验证。
B合并 / 聚合
PyramidKV / PyramidInfer 等：按层分配预算——浅层多留（细节）、深层少留（抽象），把预算从均匀分配改为金字塔分配；另有 token 级合并（相邻相似 token 的 KV 合并）。同样有损，但预算可控。
C跨层共享
YOCO / CLA（You Only Cache Once / Cross-Layer Attention）：深层直接复用浅层已算的 KV，KV 总量近似 ÷ 层数。模型架构侧改动，需模型原生支持，推理侧被动受益。
选型速判：显存吃紧先动 KV 量化（⑥ 节，fp8 KV 近无损），再考虑剪枝 / 合并（有损，按业务验收）；跨层共享看模型是否原生支持。 另有 CPU/SSD 分层卸载（LMCache / Mooncake，见 ③ 节通道 C）作为「容量换带宽」的扩容路线——量化、压缩、卸载三招可叠加，但误差也叠加，逐层验收。

⑤ 投机解码 Speculative Decoding · 用「猜-验证」换时延

原理一句话：草稿先猜 k 个 token，大模型一次 forward 并行验证，接受最长正确前缀。 数学根基是拒绝采样——接受准则保证输出分布与原模型完全一致（无损），不靠温度 hack。 收益公式：每步期望 token 数 = (1 − a^(g+1)) ÷ (1 − a)（a = 接受率，g = 草稿长度）—— 一切投机解码研究都在提高 a 或降低草稿成本。

变体谱系（按「草稿从哪来」分三代）：
  1. 独立小模型草稿：同族小模型（如 1B 起草 70B）逐 token 起草。要求同 tokenizer，否则接受率崩；需双份显存与调度；DistillSpec 用蒸馏对齐分布可再提 10~45%；
  2. 免草稿模型：n-gram / prompt-lookup——直接从 prompt 里查 n-gram 当草稿，零训练零显存，RAG / 摘要 / 代码编辑等「复述型」负载接受率 0.75~0.85，创作型仅 0.5~0.65；自投机（early-exit / LayerSkip，浅层起草全层验证，最高约 2×）；
  3. 挂在目标模型上的头（当前主流）：Medusa（多头并行预测，2.2~3.6×）；EAGLE 系（在目标模型倒数第二层特征上自回归起草，EAGLE-2 动态草稿树 3.05~4.26×，EAGLE-3 多层特征融合 + training-time test，最高 6.5×、Llama-3.3-70B 实测 3.9~4.1×、SGLang H100 上 158→373 tok/s）；MTP（DeepSeek-V3 原生多 token 预测头，随 checkpoint 发布，SGLang 首个集成，输出吞吐 +60% 口径，第 2 token 接受率 85~90%）。
引擎支持：vLLM（n-gram / EAGLE / Medusa / MTP）、SGLang（EAGLE-2/3、MTP，首个 EAGLE-3 与 MTP 集成方）、TensorRT-LLM（Medusa / EAGLE 内置）、DeepInfer（DeepSeek 生产栈的 DSpark：并行 backbone 起草 + 置信度调度验证，DeepSeek-V4 官方口径对单用户加速 60~85%）。
图示：猜-验证循环（以 g=4 为例）
接受 3 个 + 改写 1 个 = 一次全价 forward 净得 4 token。若草稿全错则白付草稿成本、只净得 1 token——收益完全由接受率决定。
适用边界（重要）：投机解码是低并发时延优化，不是万能加速—— ① 低并发 / 时延敏感（batch 1~8）：GPU 有空闲算力，验证近乎免费，收益最大（batch 1 约 1.8×，随 batch 增大递减：batch 8 约 1.25×、batch 32 约 1.05×）； ② 高并发饱和吞吐：GPU 已被真实请求填满，验证挤占算力，吞吐反而下降（MagicDec 口径：batch 32 时可跌破 1×，长上下文下可回正）——饱和吞吐场景先测再上； ③ TTFT 无益：只加速 decode 阶段，草稿模型还要额外 prefill，短输出负载净亏； ④ 负载越「可预测」接受率越高（代码 / 结构化 / 复述型 > 创作型），上线前用真实业务分布测接受率。

⑥ 量化技术对比 GGUF / FP8 / AWQ / GPTQ / bitsandbytes / NF4

降本三件套：减半显存（FP8）、扩并发（放宽 KV 精度）、省卡（INT4）。选量化先分场合： 服务端（vLLM / SGLang / TRT-LLM 双精度权重路线）vs 端与本地（llama.cpp GGUF 路线）——两条技术栈、两套命名体系，别混着比。

FP8 8-bit 浮点硬件原生
E4M3 / E5M2 · Hopper 起有 FP8 Tensor Core
浮点格式量化，校准成本最低；Hopper/Blackwell 上有 Tensor Core 加速：H100 实测吞吐 +26.7%、TTFT −20%（同精度级最大收益）。A100 及更老的卡只有省显存收益，无计算加速。
H100 及以上首选默认
AWQ INT4 · W4A16
Activation-aware Weight Quantization（MIT）
激活感知：靠校准集找出敏感通道（约 1% 权重），用 per-channel 缩放保护——不混合精度、不剪枝。质量口碑稳，同 4-bit 下通常比 GPTQ 好 1~3 分（推理 / 代码类基准）。
4-bit 服务端首选
GPTQ INT4 · W4A16
逐层 Hessian 重建 · 后处理式
最经典的 4-bit 方案，社区量化版本生态最广（TheBloke 仓库），量化出包速度快。同位宽下质量普遍略逊 AWQ；个别引擎实现有坑，上线前以目标引擎实测为准。
生态成熟 · 质量被 AWQ 反超
GGUF K-quant 2~8-bit 混精端侧专用
llama.cpp 生态 · Ollama 默认拉 Q4_K_M
分块 + 超级块、缩放因子也量化、敏感张量保高位——同位宽下质量优于老式均匀量化，Q4_K_M 实测约 4.9 bpw 而非 4.0（档位数字 ≠ 实际位宽）。I-quant（IQ 系）同体积质量更优，但偏 N 卡，CPU/Mac 上反而慢。
CPU / Mac / 单机默认 K-quant
bitsandbytes INT8 / NF4
LLM.int8() / QLoRA 的 NF4 底座
免校准、开箱即用（transformers 一行加载）；NF4 是 QLoRA 微调标配。但没有服务级 kernel 优化，吞吐明显偏低：A100 vLLM 实测 5,916 tok/s，仅为 BF16 的约 57%。
方便但慢 · 微调场景用
SmoothQuant INT8 · W8A8
激活离群值吸收后整数量化
把激活离群值按通道吸收进权重再做 W8A8 整数量化，INT8 Tensor Core 可用、质量接近 FP8，体积比 INT4 大。Ampere 时代的主流方案；在已支持 FP8 的卡上通常直接用 FP8。
Ampere 时代方案 · 新部署少用
NVFP4 / MXFP4 FP4 · Blackwell 原生硬件原生
Blackwell 代际 4-bit 浮点格式 · block 微缩放
NVFP4：block-16 微缩放（FP8 块 scale + FP32 张量 scale），精度优于 MXFP4（block-32）；MXFP4：OCP MX 标准的 32 元素块格式。吞吐收益只在 Blackwell 原生 FP4 Tensor Core 上兑现（大批量计算受限段收益最大）；Hopper 上退化为 W4A16 只省显存。TRT-LLM / vLLM 已有成熟 NVFP4 路径。注意：小模型 4-bit 掉分更多，代码 / 结构化输出类任务对 4-bit 误差敏感，上线前必须过业务验收。
Blackwell 专属 · 按业务验收
KV Cache 量化 fp8_e4m3 等
KV 精度独立于权重 · 误差乘性叠加
权重误差 × KV 误差会相乘，两头都压 4-bit 质量崩得快。KV 是显存大户（见 ④ 计算器），fp8 KV 减半占用后 H100 实测吞吐还 +1.6%。fp8 KV 需 Ada 及以上显卡支持。
长上下文显存吃紧先动 KV
选型速判
服务端 · Hopper+：FP8 权重 + FP8 KV 一步到位；
服务端 · 老卡 / 显存紧：AWQ（质量优先）或 GPTQ（生态优先）；
端侧：16GB+ 显存选 Q5_K_M / Q6_K，8~12GB 选 Q4_K_M，N 卡 4-bit 选 IQ4_XS；
微调：QLoRA（NF4 底座）；对齐评测：BF16 不量化。

⑤ 微调 → QLoRA（NF4）；对齐评测 / 蒸馏教师 → BF16 / Q8 以上；
⑥ 无论选谁，上线前拿 5 个真实业务 prompt × 候选量化档各跑一遍人工评审——困惑度和基准分不替代业务分布验证。
